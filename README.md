# AI Cycling Assistant

一个面向骑行训练管理的本地化 Web 系统，核心目标不是“记录活动”本身，而是把 **训练同步、活动复盘、补给分析、恢复建议、骑前计划、AI 教练式解读、系统运维** 串成一个完整闭环。

当前系统项目目录：`/Users/flyaways/ai-cycling-mvp`

---

## 1. 系统定位

AI Cycling Assistant 是一个以骑行为主、兼容其他运动类型的训练助手系统，具备以下几个核心方向：

- **聚合训练数据**：接入 intervals.icu 与 Strava，同步个人档案与活动记录
- **统一活动库**：把不同来源的活动去重后写入本地数据库
- **活动级分析**：对单次活动做训练负荷、节奏、疲劳、补给、恢复分析
- **骑前决策支持**：根据骑行计划生成补给携带清单与时间轴建议
- **AI 教练能力**：基于底层数据生成完整中文复盘报告，并支持追问式问答
- **自动运维能力**：带独立系统管家，支持开发版/线上版分离、发布、健康检查、看门狗、ngrok、公网入口、自启动

这不是单一页面应用，而是一个包含：

- 用户端训练产品
- 管理后台
- 多源同步系统
- 自动化任务系统
- 独立本地运维面板

的完整系统。

- 爬升
- IF
- TSS

- 用户档案
- 近期训练背景
- 补给记录

系统会生成：

- 速度/功率比

## 3.9 AI 复盘系统

核心文件：`lib/ai.ts`

系统不是简单把数据扔给模型，而是先做一层结构化上下文加工，再调用 AI。

### AI 复盘输入上下文包括
- 活动摘要
- 用户档案
- 补给实际记录
- 本地规则引擎产出的 ride review
- 本地恢复建议
- 派生特征（activity features）
- 最近活动对比
- 原始 activity attachment
- 心率解释护栏

### AI 输出能力

#### 1）完整活动复盘报告
输出字段：
- `review_text`
- `recovery_text`
- `fuel_review_text`

其中主报告会尽量包含：
- 训练性质判断
- 一句话结论
- 做得好的地方
- 可改进的地方
- 原因分析
- 训练意义
- 下次怎么练

#### 2）活动级追问聊天
支持带历史消息进行连续追问。

#### 3）流式输出
AI 报告与 AI 聊天都支持 stream 模式。

### AI 安全护栏与业务护栏
系统明确加入了若干约束：
- 不把本次活动观测最大心率误写成用户长期最大心率
- 如果补给数据未可靠填写，不会把 0 胶 / 0 饮水直接当真
- total_gels、double_gels、caffeine_gels 避免重复累计
- 数据不足时要求 AI 明确说“基于现有数据推测”

## 3.10 本地规则分析引擎

除了 AI，系统本身也有一套规则引擎。

### Ride Review 引擎
文件：`lib/engine/review.ts`

能力：
- 判断活动类型（比赛/近比赛、爬坡拉练、Endurance、短轻松骑）
- 判断高负荷刺激
- 判断爬升专项价值
- 判断心率偏高带来的恢复成本
- 判断可能补给不足
- 判断后程疲劳过重
- 输出：亮点、问题、原因、下一步建议、一句话结论

### Fuel Plan 引擎
文件：`lib/engine/fuel.ts`

能力：
- 估算骑行时长
- 按时长给碳水范围
- 根据骑行类型决定使用上限或中位值
- 判断咖啡胶使用数量
- 判断能量棒数量
- 生成补给总量、时间轴、携带清单、风险提醒
- 比较建议值与实际补给差异

### Recovery 引擎
文件：`lib/engine/recovery.ts`

能力：
- 按时长 / IF / TSS / 主观疲劳 / ATL-CTL 判断恢复等级
- 估算恢复窗口
- 生成补碳水建议
- 生成补液建议
- 标记脱水、抽筋、饿崩等警告
- 对照骑前计划评估补给偏差
- 给出次日训练建议

支持：
- 增量同步
- 全量历史回补
- 刷新 access token
- 记录 athlete profile
- Strava Webhook 接口存在：`/api/integrations/strava/webhook`

### 个人档案同步
接口：`/api/integrations/profile-sync`

支持：
- 只同步 ICU / Strava 个人资料
- 不拉活动
- 同步后更新本地用户配置与原始字段

### 自动同步任务
接口：`/api/system/auto-sync`

支持：
- 处理待同步任务
- 运行定时自动同步
- 记录最近自动同步状态

### 健康检查
接口：`/api/system/health`

返回：
- `ok`
- `service`
- `now`

## 3.12 活动去重系统

核心文件：`lib/activity-dedupe.ts`

系统支持来自多源的活动聚合，因此做了专门的去重逻辑。

### 去重依据
- 用户必须相同
- externalActivityId 相同直接视为重复
- 运动类型需一致
- 开始时间差不超过 15 分钟
- 距离 / 时长 / 爬升在容差范围内，满足至少 2 项接近

### 去重能力
- 接收 incoming activities
- 与 existing activities 比较
- 支持 alias 映射
- 结果分为：accepted / skipped
- 对跳过项保存 alias，便于后续来源映射

这能避免：
- 同一活动被 ICU 和 Strava 重复写入
- 不同源在时间略有偏移时产生重复活动

## 3.13 系统管家 / 运维面板

核心脚本：`scripts/system-manager.mjs`

这是当前系统非常完整的一块，不只是简单 PM2 替代，而是专门为本项目写的本地运维控制台。

### 基本职责
- 启动 / 停止 / 重启线上版
- 启动 / 停止 / 重启开发版
- 重新构建线上版
- 发布开发版到线上版
- 管理 ngrok
- 健康检查
- 看门狗自动拉起
- 自动同步定时触发
- 管理开机自启
- 显示用户账号列表
- 展示版本与发布状态

### 开发版 / 线上版分离

#### 开发版
- 端口：`3001`
- 使用 `next dev`
- 热更新
- 改代码后直接刷新即可看效果
- 不绑定公网入口

#### 线上版
- 端口：`3000`
- 使用构建后的 Next app
- 运行在 `.runtime/production-current`
- 绑定健康检查、看门狗、公网入口

### 发布流程
系统支持一键发布：
1. 将当前项目同步到 `.runtime/production-current`
2. 执行 build
3. 更新 productionVersion / lastPublishedAt
4. 重启线上版

### ngrok 能力
支持：
- 启动 ngrok
- 停止 ngrok
- 查看公网 URL
- 查看 ngrok 日志
- 只将 ngrok 绑定线上版

### 看门狗
每 60 秒执行一次：
- 检查线上版是否存活
- 检查健康接口是否正常
- 连续失败 3 次时重启线上版
- 检查 ngrok 是否掉线
- 掉线时尝试自动恢复

### 自动同步 tick
每 60 秒执行一次：
- 触发 `/api/system/auto-sync`
- 处理待同步任务与定时同步

### 开机自启
通过 LaunchAgent 支持：
- 安装自启
- 卸载自启
- 登录后自动启动系统管家

### 管家自带 Web 面板
会运行一个本地 HTTP 服务，默认端口：`3210`

可视化功能包括：
- 开发版状态
- 线上版状态
- 版本号
- 发布入口
- 看门狗开关
- ngrok 状态
- 日志查看
- 开机自启状态
- 用户列表

## 8. 这个系统当前最有价值的地方

如果只看“功能数量”，它已经很多；但真正最有价值的是这几个闭环：

### 闭环 1：训练同步 → 活动入库 → 去重
解决多平台活动数据统一的问题。

### 闭环 2：活动详情 → 补给记录 → 恢复建议
不是只看活动，而是把“骑完之后该怎么办”做出来了。

### 闭环 3：骑前计划 → 实际骑行 → 补给复盘
前后可以对照，形成真实训练反馈闭环。

### 闭环 4：规则引擎 → AI 深度解释
既有稳定规则判断，也有更自然的教练式复盘。

### 闭环 5：开发版 → 线上版 → 发布 → 看门狗
这套系统已经不只是产品原型，也具备持续迭代的本地运维能力。
